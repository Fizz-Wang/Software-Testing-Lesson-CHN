**测试产出物 (Testware)** 是指在执行我们之前在1.4.1节中描述的各种测试活动时，所**创建的输出工作产品 (output work products)**。可以理解为，测试过程中产生的所有文档、数据、脚本等的总称。

需要注意的是，不同的组织在如何**产生、塑造、命名、组织和管理**这些工作产品方面，存在很大的差异。并没有一个完全统一的标准说某个文档必须叫什么名字，或者必须包含哪些内容。这通常取决于组织的习惯、项目的需求以及所使用的工具。

为了确保这些测试产出物的一致性和完整性，**适当的配置管理 (Proper configuration management)** 是非常重要的（我们将在5.4节详细讨论配置管理）。配置管理能够帮助我们跟踪不同版本的测试产出物，管理变更，确保团队成员使用的是正确和最新的信息。

以下列出了一些常见的测试产出物，按照它们通常由哪个测试活动组产生来进行分类。这份清单并非详尽无遗，实际项目中可能还有其他类型的测试产出物：

- **测试策划工作产出物 (Test planning work products)** 包括：

- **测试计划 (Test plan)**：这是指导整个测试活动的最核心的文档，定义了测试的目标、范围、方法、资源、进度等。
- **测试进度表 (Test schedule)**：详细说明了各项测试活动的时间安排。
- **风险登记册 (Risk register)**：列出已识别的测试相关风险，以及每个风险发生的**可能性 (risk likelihood)**、**影响程度 (risk impact)** 和相关的**风险缓解措施 (risk mitigation)** （我们将在5.2节深入学习风险）。
- **入口准则 (Entry criteria)** 和 **出口准则 (Exit criteria)**：定义了开始某个测试阶段（例如系统测试）的前提条件，以及结束该测试阶段并认为其已完成的标准（我们将在5.1节讨论）。
- 通常，测试进度表、风险登记册、入口和出口准则等，很多时候会作为测试计划文档的一部分内容出现。

- **测试监控与控制工作产出物 (Test monitoring and test control work products)** 包括：

- **测试进展报告 (Test progress reports)**：定期向利益相关者汇报测试活动的当前状态、已完成的工作、发现的问题、存在的风险等（详见5.3.2节）。
- **控制指令文档 (Documentation of control directives)**：记录为纠正偏差或应对风险而采取的决策和行动（详见5.3节）。
- 关于风险的信息（详见5.2节）。

- **测试分析工作产出物 (Test analysis work products)** 包括：

- **（已优先排序的）测试条件 ((Prioritized) test conditions)**：例如，用户故事的**验收标准 (acceptance criteria)**（详见4.5.2节）就是一种常见的测试条件。测试条件是从测试依据中提炼出来的、需要被验证的具体方面。
- 关于**测试依据中的缺陷报告 (Defect reports regarding defects in the test basis)**：如果在分析需求文档、设计文档等测试依据时发现其本身存在问题（如描述不清、自相矛盾），并且这些问题没有被直接修正，就需要通过缺陷报告记录下来。

- **测试设计工作产出物 (Test design work products)** 包括：

- **（已优先排序的）测试用例 ((Prioritized) test cases)**：描述了为验证特定测试条件或目标而执行的一组输入值、预置条件、预期结果和执行后条件的详细步骤。
- **测试章程 (Test charters)**：通常用于探索性测试，它不像传统测试用例那样规定详细步骤，而是设定一个测试目标、范围和一些指导性想法，给予测试人员更大的自由度去探索和发现缺陷。
- **覆盖项 (Coverage items)**：在设计测试用例时，为确保测试的充分性而需要覆盖到的具体元素，例如代码的语句、分支，或需求的某个特定方面。
- **测试数据需求 (Test data requirements)**：描述了执行测试用例所需的测试数据的类型、特征和数量。
- **测试环境需求 (Test environment requirements)**：描述了执行测试所需的硬件、软件、网络、工具等环境配置。

- **测试实现工作产出物 (Test implementation work products)** 包括：

- **测试规程 (Test procedures)**：通常是一系列测试用例的有序组合，规定了它们的执行顺序。

- **手动和自动化的测试脚本 (Manual and automated test scripts)**：手动测试脚本是供测试人员遵循的详细步骤；自动化测试脚本则是用特定编程或脚本语言编写的、可由工具自动执行的程序。

- **测试套件 (Test suites)**：一组测试规程或测试脚本的集合，通常围绕某个特定功能模块、测试类型或测试目标来组织。

- **测试数据 (Test data)**：为执行测试而具体准备的输入数据。

- **测试执行计划表 (Test execution schedule)**：详细安排了何时执行哪些测试套件或测试规程。

- 测试环境项 (Test environment items)

：为支持测试执行而创建或配置的各种辅助组件。例如：

- **桩程序 (Stubs)**：在测试中用来替代被测模块所依赖的、但尚未开发完成或难以集成的模块。桩程序通常只返回预设的简单响应，以便被测模块能够继续执行。
- **驱动程序 (Drivers)**：用来调用被测模块并向其提供输入，通常用于自底向上的集成测试中。
- **模拟器 (Simulators)**：用来模拟被测软件所运行的真实环境或某些外部系统的行为，但通常模拟得不那么精确，主要关注行为接口。
- **服务虚拟化 (Service virtualizations)**：一种更高级的模拟技术，可以创建更逼真、更复杂的虚拟服务来替代那些难以获取、成本高昂或不稳定的真实依赖服务（例如第三方API）。

- **测试执行工作产出物 (Test execution work products)** 包括：

- **测试日志 (Test logs)**：详细记录了测试执行过程中的重要事件、执行的测试用例、实际结果、执行时间、环境信息等。
- **缺陷报告 (Defect reports)**：当测试发现软件的实际行为与预期结果不符（即发生失效）时，用于记录和描述该缺陷的详细信息，以便开发人员定位和修复（详见5.5节）。

- **测试完成工作产出物 (Test completion work products)** 包括：

- **测试完成报告 (Test completion report)**：总结整个测试阶段或项目的测试活动情况，包括测试覆盖范围、缺陷统计、遗留风险评估、对产品质量的总体评价等（详见5.3.2节）。
- **后续项目或迭代的改进措施清单 (Action items for improvement of subsequent projects or iterations)**：基于本次测试的经验教训，提出的具体改进建议。
- **经验教训文档 (Documented lessons learned)**：详细记录在测试过程中学到的经验和教训。
- **变更请求 (Change requests)**：例如，对于未解决的缺陷或在测试中发现的新的需求点，可能会转化为产品待办事项 (Product Backlog Items, PBI) 或正式的变更请求
